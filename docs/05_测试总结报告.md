## 8. 遗留风险与改进建议

### 8.1 遗留风险

<div style="overflow-x:auto;">

| 风险 | 影响 | 建议措施 |
|---|---|---|
| 业务码 / HTTP 状态码口径不统一 | 前端需按业务码判断，跨端对接易出错 | 制定统一错误码规范并写入接口文档 |
| 压测样本量小（5 秒 / 5 并发） | 无法反映真实并发拐点 | 加大线程数与压测时长，做阶梯压测 |
| 慢请求原因未定性 | 存在潜在性能瓶颈 | 结合慢 SQL、连接池配置、GC 日志排查 |
| 未覆盖鉴权与越权测试 | 上线后存在安全风险 | 权限体系完善后补充越权用例 |
| 数据库层 SQL 未做专项验证 | 复杂查询可能存在索引缺失 | 补充 Mapper 层 SQL 执行计划分析 |

</div>

### 8.2 流程改进建议

<div style="overflow-x:auto;">

| 改进项 | 具体做法 |
|---|---|
| 用例管理规范化 | 用例统一编号、统一模板，纳入用例库管理，便于回归复用 |
| 缺陷管理闭环 | 按「新建 → 确认 → 修复 → 待回归 → 关闭」流程流转，禁止口头修复不登记 |
| 接口文档先行 | 提测前完成 Swagger 文档评审，测试依据以文档为准 |
| 自动化补充 | 高频回归接口逐步沉淀为 Postman 集合 / JUnit 用例，减少重复手工工作 |
| 单元测试规范 | JUnit 测试类统一放 `src/test/java`，生产包不带测试代码 |

</div>

## 9. 总结与体会

本次实训完整走通了黑盒测试、白盒测试、专项测试三大板块，覆盖需求分析 → 用例设计 → 执行验证 → 缺陷跟踪 → 回归闭环的测试全流程。

**黑盒测试**方面，使用等价类划分、边界值分析、因果图决策表、正交实验、场景法、状态迁移图、思维导图七种方法，针对分诊、医生、科室、患者核心接口设计用例。不再是简单调用接口，而是结合业务规则、数据规范、状态流转去挖掘正常、异常与边界场景，有效规避业务层漏洞，体会到黑盒测试侧重业务全覆盖、保障功能可用的价值。

**白盒测试**方面，对照源码依次完成语句、判定、条件、判定-条件、条件组合、基本路径全覆盖；通过绘制控制流图、计算环形复杂度、设计独立路径用例，理清代码分支逻辑。结合目标代码插桩与 JUnit 手写 Mock 单元测试，从代码底层校验逻辑准确性，发现黑盒测试无法触及的分支漏洞，理解了白盒测试补足黑盒盲区的作用。

**专项测试**方面，用错误分析法主动排查并修复人为植入的空指针缺陷，完成「发现 → 定位 → 修复 → 回归」闭环；用 Postman 完成接口全量验证并核对 Swagger 响应；用 JMeter 完成并发压测，采集 3967 个样本、错误率 0%、平均响应 3 ms 的性能数据，验证了接口的并发承载能力。

最大收获是认识到：测试不是「随便点点看能不能用」，而是**有方法、有依据、可量化**的系统性质量保障工作——每个用例都要能说清「为什么用这个方法、覆盖了哪个风险点」，每条缺陷都要能说清「怎么复现、根因在哪、如何验证修复」。后续会继续加强用例设计的严谨性与测试流程的规范性，提升实际项目中的问题排查能力。
